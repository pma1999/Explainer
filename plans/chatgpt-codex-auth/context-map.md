# Context Map: Nuevo proveedor IA "ChatGPT / Codex CLI" (codex app-server con cuota de ChatGPT)

## Objective
Soportar el planning de una feature que añade un nuevo proveedor de ejecución: usuarios que
vinculan su cuenta de ChatGPT y el backend ejecuta el CLI de Codex (`codex app-server`) con la
cuota incluida en su plan de ChatGPT. Este mapa permite al planner localizar: auth, selector de
proveedor/modelo, pipeline de agentes, almacenamiento BYOK, despliegue, convenciones de bundle y
tests — sin rediscovery.

## Existing Patterns To Reuse
- **Patrón de proveedor completo (DeepSeek directo, el análogo más cercano)**: `backend/agents/explainer_deepseek.py` (`run_explainer_ds_validated` 381, `run_subpart_explainer_ds_validated` 423) + `backend/deepseek_client.py` (`call_deepseek_chat` 755 con retries 429/5xx y `DeepSeekUsage`) + `backend/deepseek_model_routing.py`. Un proveedor codex replica: módulo de routing, cliente (aquí: wrapper de `codex app-server`), variantes de agentes `_codex`, entrada en `main.py`.
- **Threading de config proveedor → agente**: `functools.partial(run_explainer_or, provider_routing=...)` en `_process_project` (main.py 3336-3341) — el mecanismo para inyectar opciones extra del proveedor sin tocar `_call_agent_with_optional_validation_context` (1251-1268, que solo reenvía `validation_context`/`target_language`).
- **Endpoint settings por proveedor**: pareja `POST/DELETE /api/settings/api-key/{provider}` + `_validate_{provider}_api_key` + `get_user_api_key_status` (main.py 372-517) — patrón exacto para "vincular cuenta ChatGPT" (con el matiz de que es OAuth, no API key).
- **Pre-checks de keys en `api_process_project`** (main.py 4140-4181) y fallback YouTube→Gemini (2235-2248): todo proveedor nuevo debe replicar ambos.
- **`explainer_config` persistido** (main.py 4201-4208) como contrato para on-demand (review 4354-4391, reformat 3944-3974): el nuevo provider debe persistirse ahí y resolverse en esos 3 endpoints.
- **Mascara de secretos**: `mask_api_key` (crypto.py 50-62) para logs; nunca loguear credenciales.
- **Frontend**: `persistModelSelector`/`restoreModelSelector` (landing.js 240-331) con `validProviders` hardcodeado (286); `validateExplainerProviderSelection` (338-380); patrón de listeners bajo `if (!_landingListenersAttached)` (landing.js ~955).
- **Cache TTL + degradación**: `_cache`/`_cache_lock`/`CACHE_TTL=3600` + `_fetch_openrouter_models` con stale (main.py 4530-4603) — patrón para listar "modelos/cuentas" del proveedor nuevo.
- **Honest part status**: `_format_and_finalize_part` (1959-2063) y `_failed_part_ids` — un fallo de codex por parte debe seguir este flujo (part_failed + SSE).

## Integration / Data Contracts
- **Auth**: `Authorization: Bearer <access_token GoTrue>` en todos los endpoints `/api/*`; SSE `GET /api/projects/{id}/events` acepta header Bearer (query `?token=` deprecated). El backend devuelve `user_id` (sub) como string.
- **`ProcessProjectRequest`** (body de `POST /api/projects/{id}/process`): `{explainer_provider: "gemini"|"openrouter"|"deepseek", openrouter_model?, target_language="es-ES", deepseek_model?, openrouter_provider?, openrouter_provider_only=false}`.
- **`explainer_config`** persistido en `projects`: `{provider, model, openrouter_model, deepseek_model}` — re-leído por review/reformat.
- **`user_api_keys`**: PK `(user_id, provider)`; `encrypted_api_key` Fernet derivada de `SHA256(APP_ENCRYPTION_KEY:user_id)`; RLS por fila (el backend usa service_role).
- **Provider ids de almacenamiento** (constantes `PROVIDER_*` en `supabase_data.py`): `google_gemini`, `openrouter`, `mistral`, `deepseek`, `tavily`. Validación de formato por endpoint (`_validate_*_api_key`, main.py 332-369).
- **Eventos SSE** consumidos por `frontend/js/sse.js`: `uploading | segmenting | segmented | part_started | agent_completed | part_completed | part_failed | usage_update | completed{has_failed_parts,failed_parts} | error | stream_end | ping`.
- **Contrato de agentes**: cada variante devuelve `(data, usage_meta)`; `usage_meta` expone atributos estilo Gemini (`prompt_token_count`, `candidates_token_count`, `thoughts_token_count`, `total_token_count`, `cost_usd` opcional) — ver R3.
- **Migraciones**: SQL numerado `YYYYMMDDHHMMSS_nombre.sql` con RLS; bucket Storage `project-pdfs` con path `{user_id}/{project_id}/{filename}`.

## Named Risks
- **R1 — Runtime del contenedor**: `python:3.11-slim` no tiene Node; `codex` CLI es un binario node/nativo. Dockerfile necesita instalarlo (y quizá un runtime node). Koyeb nano = 512MB RAM: un `codex app-server` por request + uvicorn + 64 threads puede exceder memoria. Verificar en `Dockerfile` + `koyeb.yaml` (instance_types nano).
- **R2 — Scale-to-zero + jobs largos**: Koyeb apaga la instancia tras ~5 min inactiva; ya existe reconciliación de PDFs interrumpidos (`INTERRUPTED_PDF_PROCESS_ERROR_MESSAGE`, main.py 168-171 + `_reconcile_stored_pdf_sources_on_startup` 244-285). Un subproceso codex en curso morirá igual; el diseño debe persistir progreso por parte (ya se hace) y marcar `error` honesto.
- **R3 — Usage/costes**: `_update_usage` (main.py 2393-2430) y `_accumulate_review_usage` (2112-2135) asumen `usage_meta` con atributos Gemini o `cost_usd` de OpenRouter; `calculate_cost` (pricing.py) requiere `model_name` en el dict. La cuota ChatGPT no produce coste USD ni necesariamente conteo de tokens — decidir cómo reflejarlo (0 coste, métrica aparte).
- **R4 — OAuth de ChatGPT ≠ API key**: el patrón BYOK existente es "usuario pega una API key". Vincular cuenta ChatGPT es OAuth (device code o callback). No existe flujo OAuth en el repo (solo email/password GoTrue); `user_api_keys.encrypted_api_key` podría guardar un refresh token OAuth cifrado con el mismo Fernet, pero el ciclo de refresh y la revocación son nuevos.
- **R5 — Cobertura por proveedor incompleta**: YouTube cae a Gemini automáticamente (2235-2248); `mermaid_agent` usa key DeepSeek hardcodeada (4272); `reformat`/`review` resuelven provider de `explainer_config` con if/elif hardcodeado (3944-3974, 4365-4391). El nuevo provider debe añadirse en TODOS estos puntos o degradar explícitamente.
- **R6 — Frontend hardcodeado a 3 proveedores**: `validProviders` (landing.js 286), `isExplainerProviderSupportedForSource` (77-81), `validateExplainerProviderSelection` (338-380), `state.has*Key` + caches (state.js 145-159, storage.js), `updateApiKeyUI` (auth.js 612-703) — cada uno lista proveedores explícitamente; un provider nuevo requiere tocar todos.
- **R7 — Strings libres**: `provider` en `user_api_keys` no tiene constraint; `explainer_provider` es un `Literal` en el request. Validación centralizada nueva (p.ej. `_resolve_explainer_model` + pre-checks) evita drift.

## Open Unknowns
- **U1 — ¿Puede el contenedor de producción ejecutar el CLI de codex?** Sin confirmar: tamaño del binario, requisitos de runtime (node versión), memoria en instancia nano de Koyeb (512MB), y si `codex app-server` necesita estado en disco persistente (auth cache) que scale-to-zero no garantiza. Verificar contra docs de Codex y el plan de Koyeb antes de decidir arquitectura (subproceso por request vs worker dedicado).
- **U2 — Flujo de vinculación de cuenta ChatGPT**: desconocido el mecanismo exacto soportado por `codex` para autenticarse sin UI (¿device-code OAuth que el usuario completa en el móvil/navegador, token API de ChatGPT?, ¿`codex login` headless?). Determina si el "settings endpoint" es una API key simple (patrón existente) o un flujo OAuth nuevo con callback/estado.
- **U3 — Interfaz no interactiva de `codex app-server`**: si soporta modo batch/JSON y si su salida puede cumplir los contratos JSON de los agentes (segmentador/explainer/recorrido/resources/review) o si habrá que envolverlo con validación adicional (patrón `*_validated`).
- **U4 — Concurrencia y cuota**: si un usuario lanza varios proyectos/partes en paralelo (`MAX_CONCURRENT_PARTS=5`), ¿cuántas sesiones `codex app-server` concurrentes tolera la cuota de ChatGPT y el sandbox del contenedor?
